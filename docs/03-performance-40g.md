# 03. Производительность на сети 40 Гбит/с

## 1. Реалистичные ожидания

Xray — один многопоточный процесс (Go): соединения клиентов распределяются по всем ядрам.

* **Шифрование** — TLS 1.3 (AES-GCM с AES-NI/VAES или ChaCha20) на каждом соединении клиента с сервером.
* **XTLS Vision + splice** (только `XRAY_TRANSPORT="vision"`; у XHTTP этого ускорения нет — для максимальной скорости на 40G выбирайте Vision): когда клиент открывает HTTPS-сайт (а это почти весь трафик), Vision после
  рукопожатия перестаёт перешифровывать уже зашифрованные сайтом данные, и на Linux ядро копирует их
  между сокетами напрямую (splice) — без копирования в пространство пользователя. Это резко
  снижает CPU на гигабит по сравнению с классическими VPN.
* **Скорость одного клиента** обычно упирается в канал клиента и RTT, а не в сервер; на
  серверных CPU одно соединение даёт единицы Гбит/с.
* **Суммарная пропускная способность** масштабируется по ядрам; 40G-канал может быть загружен
  при достаточном числе ядер и правильно настроенной сетевой карте.

Ориентир по железу для насыщения 40 Гбит/с суммарного трафика:

| Компонент | Рекомендация |
|---|---|
| CPU | 24–32+ физических ядра с AES-NI/VAES, высокая частота (≥ 3 ГГц), 1 сокет предпочтительнее (нет межсокетного трафика) |
| RAM | 32–64 ГБ (conntrack, буферы, кэш DNS, ~4–8 МБ на клиента) |
| NIC | Intel E810 / XL710, Mellanox ConnectX-4/5/6 — с RSS, ≥ 16 очередей, драйвер из ядра Debian |
| PCIe | 3.0 x8 минимум; NIC на том же NUMA-узле, что и большинство ядер |

**Всегда измеряйте на своём железе** (раздел 5) — цифры выше лишь порядок величин.

## 2. Что настраивает `04-tune-performance.sh`

### 2.1. Сетевой стек — `/etc/sysctl.d/95-vpn-performance.conf`

| Группа | Параметры | Зачем |
|---|---|---|
| Очереди ядра | `netdev_max_backlog=250000`, `netdev_budget=1200` | при пиках 40G пакеты не теряются в очереди softirq |
| Буферы сокетов | `rmem_max/wmem_max=256 МБ`, `tcp_rmem/tcp_wmem` до 256 МБ, `udp_mem` | высокий BDP: 40 Гбит/с × RTT. Сокеты Xray не упираются в буфер |
| Перегрузка | `tcp_congestion_control=bbr`, `default_qdisc=fq` | BBR держит высокую скорость при потерях и большом RTT (клиенты в интернете), fq — пейсинг |
| TCP | `tcp_mtu_probing=1`, `tcp_slow_start_after_idle=0`, `tcp_notsent_lowat`, `tcp_fastopen` | стабильность при «чёрных дырах» MTU, нет просадки после пауз, меньше задержка |
| conntrack | `nf_conntrack_max=4M`, `hashsize=1M`, короткие таймауты | Xray открывает соединения к сайтам от имени тысяч клиентов (каждый — сотни соединений): таблица не переполняется |
| Соседи | `gc_thresh*` | крупные L2-сегменты ДЦ |
| Файлы | `fs.file-max`, `nofile=1M` | тысячи сокетов и tun-устройств |

### 2.2. Сетевая карта — `vpn-nic-tune` (systemd `vpn-nic-tuning.service`, при каждой загрузке)

| Действие | Команда | Эффект |
|---|---|---|
| Ring buffers на максимум | `ethtool -G IF rx MAX tx MAX` | поглощение микровсплесков без потерь |
| RSS-очереди = физ. ядрам NUMA-узла | `ethtool -L IF combined N` | приём распределяется по ядрам аппаратно |
| GRO/GSO/TSO вкл, **LRO выкл** | `ethtool -K` | LRO несовместим с маршрутизацией (форвардингом) |
| UDP GRO forwarding | `ethtool -K IF rx-udp-gro-forwarding on` | на будущее (UDP-трафик); для Xray поверх TCP не критично |
| Адаптивная коалесценция | `ethtool -C IF adaptive-rx on adaptive-tx on` | баланс задержки и pps |
| `txqueuelen 10000` | `ip link set` | без дропов на передаче при всплесках |
| RFS | `rps_sock_flow_entries` | пакеты TCP/443 обрабатываются на ядре, где работает поток Xray этого соединения |

### 2.3. CPU и прерывания
* Governor **performance** (`cpu-performance.service`) — без просадок частоты.
* `irqbalance` распределяет прерывания очередей NIC по ядрам. Для максимальной производительности
  можно отключить его и закрепить прерывания вручную скриптом производителя
  (`set_irq_affinity` Intel, `set_irq_affinity_cpulist.sh` / `mlnx_tune` Mellanox) на ядра
  NUMA-узла карты.

### 2.4. Firewall
* Цепочка `forward` пуста и запрещена — Xray прокси, пакеты не маршрутизируются (нет NAT, нет
  накладных расходов на трансляцию адресов).

### 2.5. Xray
* `LimitNOFILE=1048576` — каждое соединение клиента и каждое соединение к сайту — дескриптор.
* `tcpFastOpen` на входящем порту — на одну задержку меньше при повторных подключениях.
* DNS — локальный кэширующий unbound (prefetch, serve-expired): разрешение имён без похода наружу.

## 3. Jumbo frames

Внутри ДЦ можно включить MTU 9000 на WAN-интерфейсе, **только если** весь путь до маршрутизатора
ДЦ поддерживает jumbo. Клиенты в интернете всё равно работают с MTU 1500. Выигрыш минимален.

## 4. Горизонтальное масштабирование

Когда одного сервера мало (или нужна отказоустойчивость):

1. **Несколько серверов с одним `/etc/xray`:** скопируйте `keys.json` и `users.json` на все узлы
   (rsync/Ansible) — одна и та же ссылка `vless://` работает на любом. Распределение — DNS
   round-robin / GeoDNS для `VPN_DOMAIN`.
2. **Отдельные ссылки на узлы** (`vpn1`, `vpn2`...) — клиенты (Hiddify, v2rayN) умеют выбирать
   лучший сервер по задержке и переключаться при недоступности.
3. **L4-балансировщик** (keepalived + IPVS в режиме DR) перед несколькими Xray — для одного IP.

## 5. Измерение

```bash
# Шифрование на этом CPU (ГБ/с на одно ядро):
openssl speed -evp aes-128-gcm -elapsed
openssl speed -evp chacha20-poly1305 -elapsed

# Пропускная способность через туннель: на клиенте, подключённом к VPN
iperf3 -c <iperf-сервер в интернете или в ДЦ> -P 8 -t 30
iperf3 -c <...> -P 8 -t 30 -R

# Нагрузочный тест суммарной скорости: N клиентов xray (JSON из `vpn-user.sh client-config`)
# на нескольких машинах-генераторах в том же ДЦ, через них — параллельные iperf3/curl.

# Наблюдение во время теста на сервере:
mpstat -P ALL 1                         # равномерность нагрузки по ядрам (пакет sysstat)
sar -n DEV 1                            # Гбит/с и pps на интерфейсе
ethtool -S enp65s0f0 | grep -Ei 'drop|miss|discard|no_buf'   # потери в NIC
nstat -az | grep -Ei 'drop|overflow|prune|RcvbufErrors'      # потери в ядре
conntrack -C                            # заполненность conntrack (пакет conntrack)
```

Признаки «узкого места»:

| Наблюдение | Что делать |
|---|---|
| Одно ядро 100% в `si` (softirq), остальные свободны | мало RSS-очередей или все прерывания на одном ядре: `ethtool -l`, `/proc/interrupts`, irqbalance |
| Растут `rx_missed`/`rx_no_buffer` | увеличить ring buffers, `netdev_budget`, проверить NUMA |
| Растут `TCPRcvQDrop` / `TCPBacklogDrop` | увеличить `rmem_*`, `netdev_max_backlog` |
| Все ядра загружены в `us` (xray) | предел шифрования CPU — масштабироваться горизонтально (раздел 4) |
