# 07. Запасной вход через CDN (Gcore, Cloudflare)

## Зачем

Если провайдер режет соединения **к IP вашего сервера** (TCP проходит, но TLS-сессия обрывается на
рукопожатии — см. диагностику в [05](05-operations.md)), никакая маскировка протокола не поможет.
Помогает другое: подключаться **не к серверу, а к CDN**. Адреса CDN обслуживают тысячи обычных
сайтов, и провайдеру видно только соединение с CDN.

```
Телефон ─TLS (SNI = cdn.ваш-домен)─▶ узел CDN ─HTTPS (SNI/Host = cdn.ваш-домен)─▶ ваш сервер :443
                                                          │ REALITY: «чужое» имя → сайт-заглушке
                                                          ▼
                                              nginx 127.0.0.1:8443 (сертификат cdn.ваш-домен)
                                                          │ секретный путь XHTTP
                                                          ▼
                                              Xray 127.0.0.1:10444 (вход vless-cdn) → интернет
```

Отдельный порт не нужен: CDN приходит на тот же 443. REALITY не узнаёт имя CDN-домена и, как
для любого постороннего посетителя, передаёт соединение сайту-заглушке; nginx по имени отдаёт
запросы с секретным путём во второй вход Xray, остальным — обычный сайт.

Прямой REALITY остаётся основным (быстрее); CDN — запасной вариант для сетей, где прямой режется.
У пользователя в приложении два профиля, работает тот, что проходит в его сети.

## Вариант 1. Gcore

В Gcore CDN — отдельный «CDN-ресурс» для одного имени (`cdn.ваш-домен`). DNS домена может
оставаться где угодно (Cloudflare, регистратор, Gcore DNS) — нужна только запись CNAME.

### 1. CDN-ресурс (CDN → Create CDN resource)

Названия пунктов в панели Gcore могут немного отличаться — важен смысл.

| Настройка | Значение | Зачем |
|---|---|---|
| Тип контента | весь сайт / динамический контент (не «только статика») | запросы XHTTP не должны кэшироваться |
| Personal domain (CNAME) | **только** `cdn.softiai.shop` — основной домен сюда не добавлять | имя, к которому подключаются клиенты; основной домен указывает прямо на сервер, Gcore не сможет выпустить на него сертификат |
| Origin (источник) | **IP сервера** `5.135.245.213`, порт **443** | |
| Origin pull protocol | **HTTPS** | на 443 у сервера только TLS |
| Change Host header (в группе источников — «Переопределение заголовка Host») | **`cdn.softiai.shop`** (или Forward Host header) | по Host nginx отличает вход CDN от основного сайта; иначе — 404 и VPN не работает |
| Change SNI hostname | Dynamic (= Host header) или Custom `cdn.softiai.shop` | REALITY не узнаёт это имя и отдаёт соединение nginx |
| HTTPS для personal domain | **бесплатный Let's Encrypt** (после того как заработает CNAME) | сертификат для участка «клиент → Gcore» |
| Кэширование | по заголовкам источника (origin controlled) или выключено | Xray отвечает `Cache-Control: no-store`; принудительный срок кэша ломает поток |
| Разрешённые методы | обязательно **GET и POST** | XHTTP packet-up отправляет данные POST-запросами |
| Ограничения доступа (WAF, rate limit, гео) | выключены | |

После создания Gcore покажет адрес ресурса вида **`cl-xxxxxxxx.gcdn.co`** — он нужен для DNS.

### 2. DNS

| Запись | Тип | Значение | Примечание |
|---|---|---|---|
| `softiai.shop` (`@`) | A | `5.135.245.213` | основной домен: REALITY и сайт-заглушка, **напрямую**, без CDN |
| `cdn` | **CNAME** | `cl-xxxxxxxx.gcdn.co` (из Gcore) | вход через CDN |

* **DNS остался в Cloudflare** — удалите старую запись `cdn` (A, оранжевое облако) и создайте CNAME
  `cdn` → `cl-….gcdn.co` с **серым** облаком (DNS only). Оранжевое облако поставит Cloudflare перед
  Gcore — так работать не будет. Настройки SSL/TLS Cloudflare для `cdn` тогда больше не важны.
* **DNS у регистратора или в Gcore DNS** — те же две записи в зоне домена (если переносили зону в
  Gcore DNS, у регистратора должны стоять NS-серверы, которые показал Gcore).
* **Gcore DNS**: запись основного домена должна быть **обычной A-записью** на IP сервера. Если в
  колонке «Подробности» у неё написано **CDN Integration**, а вместо IP — «Управляется CDN», домен
  ведёт на Gcore, а не на сервер: прямой REALITY теряет «свой» домен, а сертификат сервера не
  продлится. Уберите основной домен из CDN-ресурса, удалите эту запись и создайте A → IP сервера.
  Плюс зоны в Gcore DNS: в ресурсе можно включить **DNS-01 challenge** — сертификат выпускается
  через TXT-запись, без проверки по HTTP.
* Для основного домена CNAME не нужен и невозможен (у корня домена CNAME не допускается).

Проверка (через 5–30 минут после изменения):
```bash
dig +short cdn.softiai.shop        # первая строка — cl-xxxxxxxx.gcdn.co., дальше IP Gcore
dig +short softiai.shop            # 5.135.245.213
```
Когда CNAME заработал, включите в ресурсе Gcore бесплатный Let's Encrypt для `cdn.softiai.shop`.

### 3. Сервер

Если имя `CDN_DOMAIN` не изменилось, менять в `config.env` ничего не нужно, ссылки у
пользователей прежние. Выполните:
```bash
sudo ./scripts/03-install-vpn.sh
sudo ./scripts/vpn-user.sh selftest ivan cdn
```
Скрипт проверит, что `cdn.…` указывает на CDN, а не прямо на сервер. Сертификат сервера Let's
Encrypt он попробует расширить на CDN-домен; если проверка через Gcore не пройдёт — предупредит и
оставит сертификат только на основной домен (для Gcore этого достаточно).

## Вариант 2. Cloudflare

1. Аккаунт на cloudflare.com (тариф Free), «Add a site» → ваш домен.
2. У регистратора домена замените DNS-серверы на выданные Cloudflare (`*.ns.cloudflare.com`).
3. **DNS → Records:**
   * основной домен (`@`, для REALITY и сайта-заглушки) → IP сервера, облако **серое** (DNS only);
   * `cdn` → IP сервера, облако **оранжевое** (Proxied).
4. **SSL/TLS → Overview:** режим **Full (strict)**.
5. **Network:** `HTTP/2` и `HTTP/2 to Origin` можно оставить по умолчанию; `WebSockets` не нужен.
6. На время первого выпуска сертификата: **SSL/TLS → Edge Certificates → Always Use HTTPS — выкл.**
   (Let's Encrypt проверяет домен по HTTP; после выпуска можно включить обратно — продление
   пройдёт и через HTTPS).

### Сертификаты: зачем ещё Let's Encrypt, если у CDN уже есть

Соединение через CDN состоит из двух отдельных TLS-участков, и у каждого свой сертификат:

```
Телефон ──TLS #1──▶ узел CDN ──TLS #2──▶ ваш сервер (nginx)
          сертификат CDN          сертификат на сервере (Let's Encrypt)
```

* Сертификат на узлах CDN (Edge Certificate в Cloudflare, Let's Encrypt в ресурсе Gcore) выпускает
  сам CDN — он защищает участок «клиент → CDN».
* Участок «Cloudflare → сервер» при режиме **Full (strict)** требует на сервере действующий
  сертификат на CDN-домен; без него Cloudflare отвечает ошибкой **526**. Его выпускает `self-site.sh`
  (один сертификат Let's Encrypt на `VPN_DOMAIN` и `CDN_DOMAIN`, с автопродлением) — делать
  ничего не нужно.
* Основному домену (`VPN_DOMAIN`, без CDN) Let's Encrypt нужен в любом случае: к нему
  подключаются напрямую, мимо CDN, и REALITY показывает посетителям и сканерам именно этот
  сертификат.

Не используйте вместо этого:
* **Cloudflare Origin Certificate** — ему доверяет только Cloudflare; для `VPN_DOMAIN` браузеры и
  сканеры увидят недоверенный сертификат, и маскировка под обычный сайт пропадёт;
* режимы **Flexible** / **Full** без strict — Flexible ходит на сервер по HTTP (порт 80 отвечает
  редиректом — получится петля), Full не проверяет сертификат сервера.

## Настройка сервера (любой CDN)

`config.env`:
```
REALITY_SELF_SITE="yes"
VPN_DOMAIN="softiai.shop"
ACME_EMAIL="you@example.com"
CDN_ENABLE="yes"
CDN_DOMAIN="cdn.softiai.shop"
```
```bash
sudo ./scripts/03-install-vpn.sh                 # сертификат, vhost CDN, вход Xray
sudo ./scripts/vpn-user.sh selftest ivan cdn     # проверка всей цепочки через CDN
sudo ./scripts/vpn-user.sh link ivan             # две ссылки: REALITY и CDN
```

Скрипт проверяет, что `CDN_DOMAIN` указывает на CDN (а не прямо на сервер — серое облако в
Cloudflare или A-запись вместо CNAME у Gcore), выпускает сертификат Let's Encrypt на основной и, если
проверка через CDN проходит, на CDN-домен, и проверяет, что виртуальный хост CDN отвечает.

## Клиенты

Ссылка CDN: `security=tls`, `sni`/`host` = CDN-домен, `type=xhttp`, `mode=packet-up` (CDN пересылает
отдельные HTTP-запросы и плохо переносит длинные потоковые загрузки). Нужен клиент на ядре Xray
(v2rayNG, v2rayN, v2RayTun, V2Box…). Импорт — как обычно, из буфера или QR.

## Ограничения — честно

* **Скорость и задержка** ниже, чем у прямого REALITY: лишний узел и режим `packet-up`.
* **Доступность CDN из РФ** меняется: по сообщениям, соединения с Cloudflare и рядом зарубежных
  сетей в части российских сетей «замораживают» после первых ~16 КБ. Проверяйте из своей сети
  (ниже — тест с файлом); если один CDN режется — серверная часть та же для другого CDN.
* **Условия CDN.** Бесплатные тарифы рассчитаны на сайты; VPN-трафик через них — серая зона
  условий использования. Для нескольких пользователей обычно незаметно, при больших объёмах аккаунт
  могут ограничить.
* **IP клиентов** в `vpn-user.sh list` для CDN-подключений — `127.0.0.1` (соединение приходит через
  CDN и nginx).
* Не используйте «подмену домена» (чужое имя в SNI, свой — в Host): это нарушает правила CDN и может
  перестать работать в любой момент. Здесь SNI = ваш собственный CDN-домен.

## Проверка и диагностика

```bash
sudo ./scripts/healthcheck.sh                    # раздел «CDN»
curl -sI https://cdn.softiai.shop/               # 200, заголовки CDN (server: cloudflare / gcore)
sudo ./scripts/vpn-user.sh selftest ivan cdn
```

**Режет ли CDN ваша сеть.** `selftest` идёт с сервера через ближайший к нему узел CDN и путь из
вашей сети не проверяет. Положите на сайт файл 1 МБ и скачайте его с телефона **без VPN**:
```bash
sudo dd if=/dev/urandom of=/var/www/vpn-site/t.bin bs=1M count=1 && sudo chmod 644 /var/www/vpn-site/t.bin
# с телефона: https://cdn.softiai.shop/t.bin — должен скачаться целиком и быстро
sudo rm /var/www/vpn-site/t.bin
```
Загрузка встаёт на нескольких КБ — этот CDN в вашей сети ограничивают.

| Симптом | Причина |
|---|---|
| `selftest ... cdn` не проходит, `curl https://cdn.…/` даёт 526 | у Cloudflare Full (strict), а сертификат на сервере не содержит CDN-домен — перезапустите `03-install-vpn.sh` |
| 521 / 522 | Cloudflare не может подключиться к серверу на 443: firewall хостера, сервер выключен |
| `selftest … cdn`: `stopped after 10 redirects`, в журнале адрес `https://softiai.shop/…` | CDN забирает данные с сервера по **HTTP** (порт 80), а nginx на 80 отвечает редиректом на основной домен — петля. В ресурсе: протокол получения данных с источника **HTTPS**, порт 443 (Cloudflare: Full (strict), не Flexible). Тест с `t.bin` при этом «работает», но браузер уходит по редиректу напрямую на сервер — смотрите на адрес после загрузки |
| Gcore: 502 / 504 | ресурс не может подключиться к источнику: origin pull protocol не HTTPS, порт не 443, неверный IP |
| `https://cdn.…/` открывает сайт, а `selftest … cdn` — 404 | Host header в ресурсе Gcore не `cdn.…` (уходит на основной сайт, где нет секретного пути) |
| Gcore: «A 404 error occurred when attempting to connect to the validation URL» при выпуске Let's Encrypt | в ресурсе среди персональных доменов есть основной домен (`softiai.shop`): он указывает на сервер, и проверку Let's Encrypt получает наш nginx. В ресурсе должен быть только `cdn.…`; если основной домен не удаляется — создайте ресурс заново |
| Gcore: «A 503 error occurred when attempting to connect to the validation URL» | ресурс ещё не активен или не может получить ответ от источника. Если зона в Gcore DNS — включите в ресурсе «Использовать DNS-01 challenge»; при повторах подождите час (лимит Let's Encrypt на неудачные проверки) |
| Gcore: «The connection could not be established» при выпуске Let's Encrypt | CNAME `cdn` ещё не указывает на `cl-….gcdn.co` (или в Cloudflare у него оранжевое облако), либо ресурс ещё активируется (до 15 минут) |
| Gcore: ошибка сертификата на `https://cdn.…/` | Let's Encrypt в ресурсе ещё не выпущен: CNAME должен указывать на `cl-….gcdn.co`, затем выпустите сертификат в ресурсе |
| Сайт открывается, VPN через CDN — нет, ответы приходят «пачками» или обрываются | в ресурсе включено принудительное кэширование или не разрешён POST |
| `curl` работает, клиент — нет | старый профиль в приложении; в профиле должен быть `tls`, а не `reality`, и `packet-up` |
| Через CDN медленно | ожидаемо; для скорости используйте прямой профиль там, где он работает |
