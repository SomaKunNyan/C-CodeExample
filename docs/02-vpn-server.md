# 02. VPN-сервер Xray: VLESS + REALITY + XTLS Vision

## 1. Как это работает

[Xray-core](https://github.com/XTLS/Xray-core) принимает клиентов на **TCP/443** по протоколу **VLESS**
с транспортом **REALITY**:

1. Клиент открывает TLS 1.3-соединение, как браузер: в ClientHello — имя (SNI) **настоящего
   постороннего сайта** (`REALITY_DEST`, например `www.example.fi`) и TLS-отпечаток Chrome
   (библиотека uTLS).
2. Внутри ClientHello клиент незаметно передаёт метку, вычисленную из **публичного ключа REALITY**
   сервера и `shortId`. Только настоящий клиент может её сформировать.
3. Сервер проверяет метку:
   * **метка верна** — сервер завершает рукопожатие сам (x25519, TLS 1.3) и принимает VLESS-трафик;
   * **метки нет** (сканер, активная проверка DPI, браузер) — сервер прозрачно проксирует соединение
     на **настоящий** `REALITY_DEST`. Проверяющий получает подлинный сертификат и страницы того сайта.
4. Внутри — **VLESS** с потоком **XTLS Vision** (`xtls-rprx-vision`): идентификация по UUID
   пользователя, а TLS сайтов, которые открывает клиент, передаётся без повторного шифрования
   («TLS в TLS» без характерных для VPN размеров пакетов). На Linux данные копируются в ядре
   (splice) — очень мало CPU на гигабит.

```
Клиент ──TCP/443── TLS 1.3 (SNI=REALITY_DEST, отпечаток Chrome) ──▶ Xray
                     │ метка REALITY верна → VLESS + Vision → сайты (с IP сервера)
                     └ метки нет → прозрачно на настоящий REALITY_DEST (сервер «является» этим сайтом)
```

### Чем это лучше OpenConnect/OpenVPN/WireGuard в условиях DPI

| | OpenConnect / OpenVPN / WireGuard | VLESS + REALITY |
|---|---|---|
| Отпечаток TLS / протокола | свой, узнаваемый | как у Chrome |
| Сертификат | свой (или самоподписанный) | настоящего постороннего сайта |
| Активная проверка сервера | отвечает как VPN / молчит | отвечает как настоящий сайт |
| Нужен свой домен и сертификат | да (обычно) | **нет** |

> REALITY не защищает от блокировки **по IP-адресу** (если весь IP или подсеть хостера недоступны —
> см. [05](05-operations.md), «Если IP заблокировали»). Он защищает от распознавания протокола.

### Транспорт: XHTTP или Vision (`XRAY_TRANSPORT`)

| | **XHTTP** (по умолчанию) | **Vision** |
|---|---|---|
| Как выглядит трафик | обычные HTTP/2-запросы к сайту по пути `XHTTP_PATH` | один длинный TLS-поток |
| «Замораживание» долгих соединений после первых КБ | устойчивее (особенно `XHTTP_MODE="packet-up"`: серия коротких запросов) | уязвим |
| Скорость / CPU | немного ниже (нет splice) | максимальные (splice в ядре) |
| Клиенты | только на ядре **Xray**: v2rayNG, v2rayN, V2Box, FoXray и т.п. | все, включая sing-box (Hiddify, NekoBox) |
| Требование к `REALITY_DEST` | **обязателен HTTP/2** | HTTP/2 желателен |

Ни один транспорт не помогает, если заблокирован **IP-адрес** сервера: тогда до сервера не доходят
даже TCP-пакеты (см. [05](05-operations.md), «Если IP заблокировали»).

Режимы XHTTP (`XHTTP_MODE`, попадает в ссылки; сервер принимает любой): `auto` — с REALITY это
один поток `stream-one`; `packet-up` — отправка серией коротких POST-запросов, лучший вариант
против «замораживания», но медленнее; `stream-up` — промежуточный.

### Безопасность

* Шифрование — TLS 1.3 (x25519 / X25519MLKEM768, AES-GCM / ChaCha20-Poly1305), PFS.
* Аутентификация — 128-битный UUID на пользователя + знание публичного ключа и `shortId` сервера.
  Подбирать бессмысленно: без них сервер — просто сайт-маскировка.
* Xray работает от отдельного пользователя `xray` без root, с единственной привилегией
  `CAP_NET_BIND_SERVICE` и песочницей systemd (`ProtectSystem=strict`, `NoNewPrivileges`, ...).
* Клиенты **не могут** ходить в частные сети (сеть ДЦ, `127.0.0.1`, `10/8`...) — встроенное правило
  Xray — и на публичные адреса самого сервера (SSH, DNS) — `finalRules` в конфиге.
* SMTP (порт 25) и BitTorrent заблокированы: из-за них хостеры получают жалобы и отключают серверы.
* Российские сайты сервер **не блокирует**; открывать их лучше напрямую, мимо VPN — обход России
  в приложении или `CLIENT_DIRECT_RU="yes"` в готовом конфиге ([06](06-split-tunneling.md)): трафик
  «РФ → VPS → рунет» за доли секунды дважды пересекает границу — характерный признак прокси.
* Журнал посещённых сайтов (access log) по умолчанию **выключен**.

## 2. Выбор сайта для маскировки (`REALITY_DEST`)

Это главная настройка. Требования:

| Требование | Почему | Как проверить |
|---|---|---|
| TLS 1.3 | REALITY работает только поверх TLS 1.3 | 03-install-vpn.sh проверяет сам (`xray tls ping`) |
| HTTP/2 | так выглядят настоящие современные сайты | `curl -sI --http2 https://сайт/ -o /dev/null -w '%{http_version}\n'` → `2` |
| Не за CDN (Cloudflare, Akamai, Fastly...) | у CDN тысячи IP; несоответствие IP сайта и IP вашего сервера заметнее | `dig +short сайт` + `whois <IP>` |
| Не заблокирован в РФ, без редиректа на другой домен | иначе сервер «маскируется» под заблокированный сайт | открыть сайт из РФ |
| Желательно — в той же стране / у того же хостера, что и VPS | правдоподобная пара «IP сервера ↔ SNI» и малая задержка рукопожатия | `whois <IP сайта>` |
| **Не** «популярный» вариант из инструкций (`www.microsoft.com`, `www.google.com`, `dl.google.com`, `www.apple.com`...) | такие SNI на IP маленьких хостеров примелькались | — |

Как искать: сайты местных компаний, университетов, госучреждений, СМИ страны, где стоит VPS
(Финляндия: домены `.fi`). Проще всего — скриптом `find-dest.sh`.

### Подбор скриптом — `find-dest.sh`

```bash
# Проверить свои кандидаты (сортировка: подходящие сверху, по задержке от сервера):
sudo ./scripts/find-dest.sh check www.example.fi www.example2.fi
# Найти сайты в той же /24, что и сервер (RealiTLScanner), и сразу проверить их:
sudo ./scripts/find-dest.sh scan                 # или: scan 203.0.113.0/24 15
```

Проверяется: TLS 1.3, HTTP/2, постквантовый X25519MLKEM768, что сайт **не за CDN** (заголовки
Cloudflare, Akamai, CloudFront, Fastly, DDoS-Guard, Qrator), что главная страница **не
переадресует на другой домен** (`example.fi` → `www.example.fi` — проверьте тогда `www.example.fi`),
OCSP stapling (для сведения: Let's Encrypt OCSP больше не выдаёт), задержка TCP от сервера и
«соседство» по /24. Доступность сайта **из РФ** скрипт проверить не может — откройте его из своей сети.

**Сканирование с сервера** (`scan`) — это сотни TLS-подключений к чужим адресам с IP VPS: хостер может
принять его за сканирование сети, а наблюдатель — за странную активность. Скрипт предупреждает и
спрашивает подтверждение. Безопаснее запустить
[RealiTLScanner](https://github.com/XTLS/RealiTLScanner/releases) на своём компьютере (без VPN):
```
RealiTLScanner -addr <IP сервера>/24 -thread 4 -timeout 5 -out out.csv
```
и проверить результат на сервере: `sudo ./scripts/find-dest.sh check -f out.csv`.

Вручную то же самое:
```bash
/usr/local/bin/xray tls ping www.example.fi      # нужно: "Handshake succeeded" и "TLS Version: TLS 1.3"
curl -sI --http2 https://www.example.fi/ -o /dev/null -w '%{http_version}\n'   # нужно: 2
dig +short www.example.fi | head -1 | xargs whois | grep -Ei 'netname|org-name|country'
```

### Зеркало портов сайта (`REALITY_MIRROR_PORTS="yes"`)

У настоящего сайта обычно открыты ещё TCP/80 (редирект на HTTPS) и UDP/443 (HTTP/3), а у сервера,
который под него маскируется, — только TCP/443. С зеркалом входящие TCP/80 и UDP/443 пересылаются
(DNAT + masquerade) на сам сайт, и сканер получает те же ответы, что и от оригинала:

```
TCP/443 ─▶ Xray (REALITY)                      — как обычно
TCP/80  ─▶ nftables DNAT ─▶ настоящий сайт:80   — его редирект на https://
UDP/443 ─▶ nftables DNAT ─▶ настоящий сайт:443  — его HTTP/3 (QUIC)
```

Включение: `REALITY_MIRROR_PORTS="yes"` в `config.env`, затем `sudo ./scripts/02-firewall.sh`.
Что меняется в системе: включается IPv4 forwarding, появляется таблица `ip vpn_mirror`; цепочка
`forward` по-прежнему `policy drop` и пропускает **только** эти перенаправленные соединения (новые —
не чаще 30 в секунду с адреса). IP сайта вписывается в правила при запуске `02-firewall.sh` —
если сайт сменит IP, `healthcheck.sh` покажет ошибку, перезапустите `02-firewall.sh`. Только IPv4 и
только для чужого сайта (со своим сайтом-заглушкой порт 80 и так отвечает nginx).

### Вариант: свой сайт-заглушка (`REALITY_SELF_SITE="yes"`)

Вместо чужого сайта REALITY может маскироваться под **собственный небольшой сайт на вашем домене**:

```
Посетитель / сканер ──TCP/443──▶ Xray ──(нет ключа клиента)──▶ nginx 127.0.0.1:8443 ── сайт на VPN_DOMAIN
Клиент VPN ─────────TCP/443──▶ Xray ──(ключ верен)──▶ VLESS → интернет
Порт 80 ────────────────────▶ nginx: Let's Encrypt + редирект на https://VPN_DOMAIN
```

Плюсы: SNI в подключениях — **ваш домен, который действительно указывает на IP сервера** (у чужого
сайта IP другой); не зависите от доступности и настроек постороннего сайта; браузер на
`https://ваш-домен` показывает обычный сайт небольшой компании с настоящим сертификатом.

Что нужно в `config.env`:
```
REALITY_SELF_SITE="yes"
VPN_DOMAIN="softiai.shop"       # A-запись -> публичный IP сервера
ACME_EMAIL="you@example.com"     # уведомления Let's Encrypt
SITE_TITLE=""                    # название на сайте; пусто = из домена
```
Затем `sudo ./scripts/02-firewall.sh` (откроет порт 80) и `sudo ./scripts/03-install-vpn.sh`
(вызовет `scripts/self-site.sh`: nginx, сайт из `templates/site/`, сертификат с пробным выпуском,
автопродление). `REALITY_DEST` и `REALITY_SERVER_NAMES` в этом режиме не используются; ссылки
меняются (SNI = ваш домен) — раздайте новые. Сайт можно заменить своими страницами: файлы в
`/var/www/vpn-site/` (шаблоны — `templates/site/`).

## 3. Установка — `03-install-vpn.sh`

В `config.env` задайте как минимум `REALITY_DEST`, затем:
```bash
sudo ./scripts/03-install-vpn.sh
```

Что делает скрипт:

1. **Xray** — скачивает релиз `XRAY_VERSION` (по умолчанию последний) с GitHub XTLS, **проверяет
   SHA-256** из файла `.dgst` релиза, ставит `/usr/local/bin/xray` и geo-базы в `/usr/local/share/xray`.
2. **Ключи** — `xray x25519` (приватный/публичный ключ REALITY) и случайный `shortId` → `/etc/xray/keys.json`
   (только root). Генерируются **один раз**: повторный запуск их не меняет, ссылки клиентов остаются рабочими.
3. **Проверка `REALITY_DEST`** — TLS 1.3 обязателен, HTTP/2 и постквантовый обмен ключами — желательны.
4. **unbound** — локальный DNS-резолвер с DNSSEC, слушает только `127.0.0.1`: Xray разрешает через
   него домены, к которым обращаются клиенты (без сторонних DNS-сервисов).
5. **Конфигурация** — `/etc/xray/config.json` генерируется `scripts/xray-vpn.py` из `keys.json` и
   `users.json`, проверяется `xray run -test` **до** применения; при ошибке остаётся прежняя.
6. **systemd** — `xray.service` (пользователь `xray`, песочница, автоперезапуск), аудит `/etc/xray`.

Файлы на сервере:

| Файл | Содержимое | Права |
|---|---|---|
| `/etc/xray/keys.json` | ключи REALITY, shortId | root, 0600 |
| `/etc/xray/users.json` | пользователи (имя, UUID, вкл/выкл) | root, 0600 |
| `/etc/xray/config.json` | конфигурация Xray (генерируется) | root:xray, 0640 |

Не редактируйте `config.json` вручную — он перезаписывается при каждом изменении пользователей.

## 4. Пользователи

```bash
sudo ./scripts/vpn-user.sh add ivan             # создать: ссылка vless:// + QR-код
sudo ./scripts/vpn-user.sh link ivan            # показать ссылку и QR снова
sudo ./scripts/vpn-user.sh list                 # все пользователи, трафик, кто онлайн, с каких IP
sudo ./scripts/vpn-user.sh lock ivan            # заблокировать (сессии сразу рвутся)
sudo ./scripts/vpn-user.sh unlock ivan
sudo ./scripts/vpn-user.sh reset ivan           # новый UUID: старая ссылка перестаёт работать
sudo ./scripts/vpn-user.sh del ivan
sudo ./scripts/vpn-user.sh client-config ivan > ivan.json   # полный JSON с исключениями (см. 06)
```

В ссылке адресом сервера стоит его **публичный IP** (`LINK_ADDRESS="ip"`, по умолчанию): подключение
не зависит от DNS у клиента. Если VPS за NAT хостера (на интерфейсе `192.168.x.x`), публичный IP
определяется автоматически; надёжнее вписать его в `PUBLIC_IPV4`. Ссылки с доменом —
`LINK_ADDRESS="domain"` + `VPN_DOMAIN`.

Ссылка `vless://…` — это и есть доступ: передавайте её только владельцу по защищённому каналу. Если
ссылка утекла — `reset`. Изменение пользователей перезапускает Xray (≈1 с): клиенты переподключаются
автоматически.

## 5. Проверка

На сервере:
```bash
sudo ./scripts/healthcheck.sh
systemctl status xray
journalctl -u xray -f
```

Снаружи — сервер должен быть неотличим от сайта-маскировки:
```bash
curl -sI --resolve www.example.fi:443:<IP-сервера> https://www.example.fi/   # заголовки настоящего сайта
```

С клиента: подключиться (см. [04](04-clients.md)), открыть https://ifconfig.me — должен быть IP сервера.

## 6. Частые проблемы

| Симптом | Причина / решение |
|---|---|
| `03-install-vpn.sh`: «не отвечает по TLS 1.3» | выберите другой `REALITY_DEST` |
| Клиент не подключается, на сервере тишина в `journalctl -u xray` | соединение не доходит до сервера: блокировка IP по пути, проверьте `nc -vz <IP> 443` из той же сети |
| Клиент не подключается, ошибки REALITY в логе клиента | неверные `pbk`/`sid`/`sni` в клиенте — переимпортируйте ссылку (`vpn-user.sh link`); проверьте время на телефоне |
| Подключается, но сайты не открываются | `systemctl status unbound`; `dig @127.0.0.1 example.com`; возможно, пользователь заблокирован (`list`) |
| Работало и перестало у всех из одной сети | блокировка IP — см. [05](05-operations.md), «Если IP заблокировали» |
